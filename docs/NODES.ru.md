# Репозитории и узлы WARP

Язык: [English](NODES.md) | Русский

**Статус: проект, не реализовано.** Названия команд и полей предварительные.

## Зачем

- **Режим репозитория** — любой человек или компания разворачивает свой репозиторий пакетов одной-двумя командами.
- **Режим узла** — узлы берут на себя раздачу всех пакетов репозитория или их части. Это снимает нагрузку с хоста репозитория и даёт горизонтальное масштабирование.
- **Подключение репозиториев** у клиента уже есть (`warp repo add … --pubkey`) и остаётся главным способом доверять репозиторию.

## Главный принцип

Мир пакетов закрыт: пакет существует только тогда, когда его имя, версию и sha256 подписал репозиторий. Узлы — транспорт. Они не могут добавить пакет, изменить его или подсунуть другую версию: клиент сверяет каждый скачанный байт с подписанным индексом.

Для подписи репозиторию не нужен сам файл, только его sha256. Поэтому пакет может лежать только на узлах (если у хоста кончилось место или трафик), но подписан он всё равно репозиторием.

## Роли ключей

Сейчас один ключ делает всё. Чтобы кража одного ключа не давала выпустить вредонос, роли разделяются:

| Ключ | Где живёт | Что подписывает | Что будет при краже |
|---|---|---|---|
| Корневой | офлайн | `root.json`: какие ключи ниже действуют и до какого срока | всё — поэтому он офлайн и используется редко |
| Ключ индекса | не на сервере раздачи | `index.json`: пакеты, sha256, дельты | можно подписать вредонос — меняется корневым ключом |
| Онлайн-ключ | на сервере | `nodes.json` и `timestamp.json` с коротким сроком | только список узлов и свежесть, в пределах срока; пакеты подписать нельзя |

Закреплённый у клиента ключ (сегодняшний `--pubkey`) становится корневым. Смена ключей ролей — новый `root.json`, подписанный корневым ключом. Смена самого корневого ключа — новый `root.json`, подписанный и старым, и новым корневым ключом.

## Файлы репозитория

| Файл | Подпись | Срок годности | Содержимое |
|---|---|---|---|
| `root.json` | корневой ключ | длинный (например, год) | ключи ролей и их сроки |
| `index.json` | ключ индекса | средний | пакеты, sha256, размеры, дельты, где лежат; растущий номер `version` |
| `nodes.json` | онлайн-ключ | короткий (например, сутки) | сертификаты узлов |
| `timestamp.json` | онлайн-ключ | очень короткий (например, час) | номер версии и sha256 актуальных `index.json` и `nodes.json` |

## Защита от отката — первый этап

Сейчас клиент читает `timestamp` индекса, но не сравнивает его с уже виденным. Любой, кто раздаёт индекс, может отдать старый, но честно подписанный индекс, и клиент застрянет на версиях с известными уязвимостями. Поэтому до узлов:

- у каждого подписанного файла есть растущий номер `version` и срок годности `expires`;
- клиент хранит последний виденный номер и отказывается от файла с меньшим номером или просроченного, с понятной ошибкой.

Без этого режим узла не включается.

## Сертификат узла

Запись в `nodes.json`:

```json
{
  "node_id": "fra-1",
  "pubkey": "<Ed25519-ключ узла>",
  "urls": ["https://mirror.example/warp"],
  "scope": {"packages": ["rust", "go"]},
  "issued": "2026-09-23T12:00:00Z",
  "expires": "2026-09-24T12:00:00Z"
}
```

`scope` — все пакеты или их часть: список имён или диапазон хэшей для равномерного шардирования.

## Подключение узла — согласие обеих сторон

1. **Оператор узла** создаёт ключ узла и отправляет репозиторию запрос: ключ, адреса, какую часть готов хранить. Запрос подписан ключом узла — так узел доказывает, что ключ его.
   `warp node init` → `warp node request <url-репозитория>`
2. **Владелец репозитория** видит запрос и одобряет его с областью и сроком.
   `warp repo nodes pending` → `warp repo nodes approve <id> --scope … --days N`
3. **Синхронизация.** Узел скачивает пакеты из своей области и проверяет каждый по sha256 из подписанного индекса. Не совпало — не раздаёт.
4. **Проверка готовности.** Репозиторий запрашивает у узла случайные фрагменты пакетов из его области. Только после ответа узел попадает в `nodes.json`.
5. **Продление.** Онлайн-ключ регулярно пересобирает `nodes.json` с новым сроком, но только для узлов, которые прошли проверку доступности. Пропавший узел выпадает при следующем продлении сам.
6. **Отзыв.** Узел убирается из `nodes.json`; клиенты узнают при следующем `timestamp.json`.

По умолчанию в репозиторий попадают только одобренные узлы. Открытая регистрация — возможная опция позже: её проще засорить мёртвыми адресами. Нынешние `warp seed` / `warp volunteer` становятся частным случаем узла.

## Как клиент качает

1. `warp update`: `timestamp.json` → `index.json` и `nodes.json`. Проверяются подписи, номера версий и сроки.
2. Для пакета собираются кандидаты: сам репозиторий и узлы с непросроченным сертификатом, в чью область входит пакет.
3. Клиент пробует их по очереди (по задержке или случайно) и сверяет sha256. Не совпало, ошибка или медленно — узел помечается плохим, берётся следующий.

## Пакеты от узлов — делегирование, а не своя подпись

Узел **не подписывает** пакеты от имени репозитория: иначе взломанный узел выпустит вредонос под чужим доверием. Если узлу нужно публиковать своё:

- **отдельный репозиторий** со своим ключом — пользователь добавляет его явно;
- **делегирование пространства имён** — корневой ключ разрешает ключу узла подписывать только пакеты с префиксом, например `acme/*`. Клиент показывает источник, а базовые пакеты (`warp`, `openssl` и т. п.) узел перекрыть не может.

## Риски

- **Приватность:** узел видит IP клиента и что тот качает. Для компаний это нужно указать явно.
- **Недоступные и медленные узлы:** клиент молча переключается на другие узлы или на репозиторий.
- **Кража онлайн-ключа:** можно испортить список узлов или задержать обновления в пределах срока `nodes.json` / `timestamp.json`, но нельзя подписать пакет.

## Этапы

1. Защита от отката.
2. Режим репозитория: `warp repo init` и `warp publish` вместо внешнего скрипта, раздельные ключи.
3. Режим узла: сертификаты, согласие, синхронизация, проверка, продление, скачивание клиентом с узлов.
4. Делегирование пространств имён (по необходимости).
